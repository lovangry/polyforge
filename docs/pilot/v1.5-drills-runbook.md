- **结论先行**：健康系统在 D1–D5 中必须产出三类 typed refusal，且断言的是**逐字**命中：
  1. **GIT-401 且点名新持有者**——被接管方的 git push 在 aihub 代理处被拒，wire 面 HTTP 401 + 响应头 `X-PF-Git-Error: GIT-401`（curl -D 实际显示 Go 规范大小写 `X-Pf-Git-Error`，断言一律 `grep -i`）+ body `credential rejected: the work item is held by session <新指纹>`（`internal/aihub/core/owner.go`：`Fail(api.ErrGitUnauthorized, "BAD_CREDENTIAL", "credential rejected: the work item is held by session %s", fp.String)`）；
  2. **CORE-403 STALE_SESSION**——被接管方的 session-end（pause/wrap）被拒：`CORE-403: session does not match the current holder <新指纹>`（`internal/aihub/core/session.go` 的 `End`/`Pause`/`Attach` 共用 refusal；wire 面 `extra.reason=STALE_SESSION`，CLI 面印 `pf: CORE-403: ...`，退出码 1）；
  3. **quarantine 命名**——旧 capsule 原地改名 `capsules/<wi_id>.quarantined.<ts>`（`internal/polyforge/runtime/runtime.go` `quarantineCapsule`：`<id> → <id>.quarantined.<ts>`，ts 为 UnixNano 的 36 进制；**改名不删除**），且被接管方的 release/supersede **不做任何 hub 转移**（新持有者的 session 与 status 原样不动）。

### 0.2 每条演练的公共准备序列

```sh
# 1) 开一张慢票：10 分钟 sleep 保证演练窗口内 WI 一直 running（fakepi 按 plans/<id>.json 驱动）
WI=$(new_wi d1-takeover-fencing \
  '{"actions":[{"do":"step","id":"s1"},{"do":"sleep","ms":600000},{"do":"step","id":"s2"},{"do":"wrap"}]}')

# 2) 提交到 daemon a，等它 running，记下公开指纹（B3：指纹是公开句柄，秘密永不回显）
pfa submit $WI                    # → submitted <wi> (accepted by the local daemon)
wait_status $WI running           # 等 aihub 侧 status=running
FP_A=$(wi_session_fp $WI)         # a 的 session_fingerprint（16 hex）
wi_machine $WI                    # → m-v15-a

# 3) 本手册自备的观测/重启助手。观测一律走 GET /jobs/<id>/observe（daemon UDS 面的 JobView
#    即挂在 observe 路由上，cli/daemon.go 的路由族同此）；common.sh 的 job_view 打的
#    GET /jobs/<id> 不在当前 daemon 路由表内，勿用。
job_json()  { curl -s --unix-socket $P/$1/daemon.sock "http://localhost/jobs/$2/observe?after=0"; }
job_field() { job_json "$1" "$2" | python3 -c "import json,sys; print(json.load(sys.stdin).get('$3',''))"; }
hub_events() { curl -s -H "Authorization: Bearer $KEY" "$S/api/v1/work-items/$1?include=events" | \
  python3 -c 'import json,sys
d=json.load(sys.stdin)
for e in d.get("attrs",{}).get("events",[]): print(e["type"], json.dumps(e["payload"]))'; }
restart_daemon() {  # 单 daemon 重拉（boot.sh 的单机版；切勿用 boot.sh 重启单个 daemon，见 §6）
  m=$1
  [ -f $P/$m/daemon.pid ] && kill -9 "$(cat $P/$m/daemon.pid)" 2>/dev/null
  env FAKEPI_PLANS=$P/plans setsid $V/pf daemon \
    -server $S -api-key "$KEY" \
    -workflows-dir $REPO/workflows -executor-prompt $REPO/skills/pf-execute/SKILL.md \
    -max-concurrent-jobs 4 -mode interactive -project polyforge \
    -data-dir $P/$m -socket $P/$m/daemon.sock \
    -workspace-root $P/$m/ws -machine-id m-v15-$m \
    -pi-bin $V/fakepi -harness-sessions-root $P/$m/ws/sessions \
    >> $P/$m/daemon.log 2>&1 &
  echo $! > $P/$m/daemon.pid
}
```

## 1. D1：跨机接管 fencing（takeover fencing）

- **目的**：验证「fencing-on-use, not invalidation-on-claim」（`v1.5-session-model.md` M 裁定第 3 条/行业研究第 5 条）：b 的 `pf submit --takeover` 原子换掉 aihub 的 session 行后，**a 的凭证没有被吊销、也没有任何人通知 a**——a 的一切写用面（git push、session-end）在下一次使用时才被拒，且拒绝语必须**点名新持有者的公开指纹**，让 a 可自诊（`v1.5-api-contract.md#§1.4/§1.5/§1.6`）。
- **机制引用**：接管 = `internal/aihub/core/session.go` `Takeover`（单事务换 `session_hash/fingerprint/machine/owner`，事件 `session_superseded` 携带 OLD 指纹，m4 审计）；push 面 = `owner.go` `CheckPushCredential`（`hex(sha256(password)) == session_hash AND status==running`）；wire 面 = `git/proxy.go`（typed code 走 `X-PF-Git-Error` 头，git 客户端只见 401）。

操作序列（续用 §0.2 的 `$WI`，此时 a 持有、`FP_A` 已记录）：

```sh
# 0) 基线：a 的秘密在其 runtime-state.json（除一次性 askpass 外唯一落点）
OLD_SECRET=$(python3 - <<EOF
import json
d = json.load(open("$P/a/runtime-state.json"))
print(next(j["session_id"] for j in d["jobs"] if j["work_item_id"] == "$WI"))
EOF
)
grep -q '"kind":"published"' $P/a/events.log    # 等首个链提交（bare 仓已建）
curl -s -o /tmp/probe.body -D /tmp/probe.hdr -u "$WI:$OLD_SECRET" \
  "$S/git/$WI.git/info/refs?service=git-receive-pack"
head -1 /tmp/probe.hdr        # → HTTP/1.1 200 ...（接管前凭证有效）

# 1) b 强制接管（daemon 侧接管；CLI 侧 `pf takeover` 会留下孤儿 session，见 §6）
pfb submit $WI --takeover

# 2) 等 hub session 行被原子换掉：新指纹、机器 m-v15-b
while [ "$(wi_session_fp $WI)" = "$FP_A" ]; do sleep 0.5; done
FP_B=$(wi_session_fp $WI)
wi_machine $WI                                     # → m-v15-b
hub_events $WI | grep session_superseded           # → session_superseded {"old_session_fingerprint": "<FP_A>", "new_session_fingerprint": "<FP_B>", ...}
until [ "$(job_field b $WI status)" = "running" ]; do sleep 0.5; done
job_field b $WI spawn_n                            # → 2（B2：接管克隆从 capsule 的 spawn journal 重新起算，契约 §4.3）

# 3) fencing 探针一：旧秘密的 git 面被拒，点名新持有者（与 test/v1_s11_takeover_test.go 的 wire 断言同型）
curl -s -o /tmp/probe.body -D /tmp/probe.hdr -u "$WI:$OLD_SECRET" \
  "$S/git/$WI.git/info/refs?service=git-receive-pack"
head -1 /tmp/probe.hdr                             # → HTTP/1.1 401 Unauthorized
grep -i "x-pf-git-error: GIT-401" /tmp/probe.hdr   # → X-Pf-Git-Error: GIT-401
cat /tmp/probe.body   # → {"code":"GIT-401","detail":"credential rejected: the work item is held by session <FP_B>"}

# 4) fencing 探针二：旧持有者的 session-end（operator pause 走 session-end 的 paused 判定）被拒
if pfa pause $WI > /tmp/pause.out 2>&1; then echo "D1 FAIL: session-end was accepted"; else echo "exit=$?"; fi
cat /tmp/pause.out     # → pf: CORE-403: session does not match the current holder <FP_B>
```

断言（复制即跑；全部通过印 `D1 OK`）：

```sh
grep -qi '^x-pf-git-error: GIT-401' /tmp/probe.hdr && \
grep -q "credential rejected: the work item is held by session $FP_B" /tmp/probe.body && \
grep -q "CORE-403: session does not match the current holder $FP_B" /tmp/pause.out && \
[ "$(wi_status $WI)" = "running" ] && [ "$(wi_session_fp $WI)" = "$FP_B" ] && echo "D1 OK"
```

- **实测对照**（2026-10-01，`wi_orqSy3q6dYb3`）：rig 照录的 fenced push 在 daemon 事件面的呈现（git 客户端只认 HTTP 401；typed `GIT-401` 在代理响应头里，即探针三所见）：
  `"error":"GIT-500: : git push --push-option=session-fingerprint=f7137b9b17606d74 http://127.0.0.1:8425/git/wi_orqSy3q6dYb3.git HEAD:refs/heads/main: fatal: Authentication failed for 'http://127.0.0.1:8425/git/wi_orqSy3q6dYb3.git/'"`（`push_failed` 事件，`a/events.log` 原文；外层 `GIT-500` 是 daemon 侧对 git 客户端失败的包装上报，底层拒绝即 401）。
- **健康系统不得做的事**：旧持有者的 push **不得**成功；旧持有者的 session-end **不得**被接受（不得产生任何 hub 转移）；拒绝语**不得**省略新持有者指纹（B3/m4：被接管方靠它自诊，不需要看到任何秘密）；接管**不得**依赖「通知旧方」——fencing-on-use 是唯一正确层，信号只是加速（`v1.5-session-model.md` 附录第 5 条）。
- **时序注意**：探针必须在接管后 **5 分钟内**完成——a 的 M4 会话复验（见 D5）一旦先发现被接管，会就地 release，此后 `pfa pause` 只会答 `pf: DAEMON-404: no local job for <wi> on this daemon`。步骤 4 的 pause 会先杀 a 的本地 agent 树；在单机 rig 上该清理可能波及 b 的 agent（L4 按 `PF_WI_ID` 全机扫描，见 §6），健康表现是 b 的 daemon 自愈重派（同指纹、spawn_n+1）——可顺手断言 `job_field b $WI status` 回到 `running`。

## 2. D2：崩溃续跑对账（restart reconciliation：match → resume）

- **目的**：验证 `internal/polyforge/runtime/restart.go` 的对账主分支：daemon 崩溃（未经优雅停机）重启后，先 B1 journal replay，再对 state.json 每条记录做 compare-only 的 `SessionVerify`（B3：hub 只存哈希）——**verify matches + status=running ⇒ 崩溃中续跑**：杀残留树、经恢复引擎原地续跑。同机恢复 **session_id 不变**，派生计数 `spawn_n` 单调 +1（`v1.5-session-model.md` 核心机制；`recover.go`：`ordinal := spawnN + 1`；env 注入 `PF_SPAWN_N`/`PF_SESSION_HANDLE`，`spawn.go`）。
- **与 v1 的对照**：v1 以 attempt/instance 谱系判新旧；v1.5 的身份对是 `(session_fingerprint, spawn_n)`（契约 §4.3），本演练断言的正是这对身份。

操作序列：

```sh
# 0) 基线
FP_A=$(wi_session_fp $WI); job_field a $WI spawn_n    # → 1
# 1) 崩溃：kill -9（不是优雅停机；a 的 agent 成了孤儿进程——这正是要验的现场）
kill -9 "$(cat $P/a/daemon.pid)"
# 2) 单机重拉（§0.2 的 restart_daemon；勿用 boot.sh）
restart_daemon a
# 3) 等对账收敛：hub 全程未动，a 侧重新 running
until [ "$(job_field a $WI status)" = "running" ]; do sleep 0.5; done
```

断言：

```sh
[ "$(wi_session_fp $WI)" = "$FP_A" ] && \
[ "$(wi_status $WI)" = "running" ] && \
[ "$(job_field a $WI session_fingerprint)" = "$FP_A" ] && \
[ "$(job_field a $WI spawn_n)" -eq 2 ] && \
grep -q '"kind":"job_started","work_item":"'$WI'"' $P/a/events.log && \
grep -q '"spawn_n":2' $P/a/events.log && echo "D2 OK"
# 人读面：pfa ops status 的 spawn 列应显示 #2、session 列仍是 FP_A
```

- **实测对照**：同会话恢复/接管克隆后派生计数不归零——`b/events.log`（接管方的克隆续跑）出现 `"spawn_n":2` 与 `"spawn_n":3` 两档（`maxSpawnNFromJournal` 重播种 + 后续崩溃恢复各 +1），与 `test/v1_s11_takeover_test.go` 对接管方首派生计数的断言（`bSpawn != 2` 即 fatal："want 2 (re-seeded from the cloned spawn journal)"）同源。
- **健康系统不得做的事**：指纹**不得**变化（变化=新会话，等于把崩溃当成了接管）；spawn_n **不得**回到 1（那会撞坏 flush fence，B2）；hub status **不得**翻转；对账**不得**只信 state.json（`restart.go` 头注：every recorded job is reconciled against aihub's own verdict first）。

## 3. D3：优雅停机恢复（graceful shutdown resume）

- **目的**：验证 `internal/polyforge/daemon/shutdown.go` 的停机语义：优雅停机**不**做 session-end——「Jobs are NOT session-ended here: the WIs stay running server-side (our session row intact, the records keep clean_pause=false ...)」（`shutdown.go` 头注原文；停机预算 `ShutdownBudget` 5 min、每 job flush(shutdown) 等待 60 s）。因此 hub 侧 WI 保持 **running**、session 行原样；重启后对账走 D2 的同一分支续跑。（设计记录 `v1.5-session-model.md` 的 M3 草图写的是停机置 paused；落地实现**刻意不走** pause 迁移——`shutdown.go` 头注原文："the hub's pause transition exists and is reached through session-end's paused verdict, but the shutdown deliberately does not use it"。`restart.go` 里 paused+clean_pause=false 的 SessionAttach 分支保留给 hub 果真记录了停机 pause 的形状。）
- **操作序列**：

```sh
FP_A=$(wi_session_fp $WI)
# 1) 优雅停机（= ops 的 shutdown，即 04 §6.5 的 quiesce；不是 Drain）
pfa ops shutdown                 # → graceful shutdown requested; the daemon quiesces and exits
while kill -0 "$(cat $P/a/daemon.pid)" 2>/dev/null; do sleep 0.5; done   # 等进程退出

# 2) 断言 hub 侧纹丝不动：running、同指纹、非 clean-pause
wi_status $WI                    # → running
wi_session_fp $WI                 # → FP_A
wi_field $WI clean_pause          # → False

# 3) 重启 a：对账 verify-matches + running ⇒ 恢复引擎续跑（transcript resume）
restart_daemon a
until [ "$(job_field a $WI status)" = "running" ]; do sleep 0.5; done
```

断言：

```sh
[ "$(wi_status $WI)" = "running" ] && [ "$(wi_session_fp $WI)" = "$FP_A" ] && \
[ "$(job_field a $WI spawn_n)" -eq 2 ] && \
[ "$(job_field a $WI session_fingerprint)" = "$FP_A" ] && echo "D3 OK"
```

- **健康系统不得做的事**：停机**不得**把 WI 收成 paused/wrapped/blocked（hub 状态必须一字不动）；**不得**清 session 行（`v1.5-session-model.md`：Graceful shutdown: session_id stays on WI）；重启**不得**开新会话（新会话=把停机当接管，只有 `--takeover` 才允许换 holder）。

## 4. D4：停机后接管（shutdown-then-takeover）

- **目的**：串起 D3 的停机形状与 D1 的接管：a 优雅停机（WI 在 hub 侧仍被 a 的会话持有、status=running）→ b `--takeover` 合法接管（`Takeover` 门：running 或 paused 皆可）→ **重启旧持有者 a**，其对账走 mismatch 分支：`restart.go`——「running or paused under ANOTHER session (the takeover happened while we were down): release — kill any local tree, quarantine the capsule, drop the record. NO hub transition: the new owner owns the work.」quarantine 命名即 `runtime.go` `quarantineCapsule`：`capsules/<id> → capsules/<id>.quarantined.<ts>`。

操作序列：

```sh
# 1) a 优雅停机（hub 侧：仍 running、仍 FP_A——同 D3 断言）
pfa ops shutdown
```

## 6. 汇总与运维注意事项

**三类 typed refusal 的落点速查**：

| 类别 | wire/文件面 | 人读面（CLI） | 权威 |
|---|---|---|---|
| GIT-401（点名新持有者） | HTTP 401 + 头 `X-Pf-Git-Error: GIT-401` + body `{"code":"GIT-401","detail":"credential rejected: the work item is held by session <fp>"}` | git 客户端 `fatal: Authentication failed for '<remote>'`；daemon events.log 的 `push_failed` | `owner.go` / `git/proxy.go` / `errors.go` `ErrGitUnauthorized` |
| CORE-403 STALE_SESSION | aihub 面 `{"code":"CORE-403","detail":"session does not match the current holder <fp>","extra":{"reason":"STALE_SESSION"}}`（daemon 转发面同型封套） | `pf: CORE-403: session does not match the current holder <fp>`，退出码 1（4xx→1，5xx→2） | `session.go`（`End`/`Pause`/`Attach`/幂等缓存 `replay`） |
| quarantine 命名 | `capsules/<wi_id>.quarantined.<ts>`（UnixNano 36 进制；改名不删除） | `a/daemon.log` 的 `... — local tree killed, capsule quarantined, record dropped (no hub transition)` 行 | `runtime.go` `quarantineCapsule`（契约 §4.4 同名） |

**运维注意事项**：

- **boot.sh 是全新 rig 的入口，不是重启器**：它先按 pid 文件 kill 旧 aihub + 双 daemon，再 `rm -rf aihub-data` 重建 DB、重发新 key——用它"重启单个 daemon"会连带毁掉全部演练现场与 root.key。单 daemon 重启用 §0.2 的 `restart_daemon a|b`。
- **单机 rig 的共享内核边界**：两台"机器"共享一个内核时，六层清理的 L4（`cleanup.go`：`/proc/*/environ` 含 `PF_WI_ID=<wi>` 即杀，daemon 无关）会把对方 daemon 的同 WI agent 一并收走。健康系统必经的自愈路径是：幸存 daemon 的 monitor 发现 agent 死亡 → `OBNeedsRecovery` → `recoverOp` 同会话重派（指纹不变、spawn_n+1）。每条涉及清理的演练（D1 尾步、D4、D5）都应顺手断言幸存方回到 running；真双机 rig 无此现象（`test/v1_s11_takeover_test.go` SHAPE NOTE 有同样交代）。
- **daemon 侧 vs CLI 侧接管**：演练一律用 `pf submit <id> --takeover`（daemon 侧：ForceTakeover + 克隆 capsule + 派生 agent）。CLI 侧 `pf takeover <id> --reason ...` 只换 hub session、不启动任何东西（`verbs_aihub.go` NOTE 8："the WI is held by an orphan session after this"），仅适合制造"孤儿会话"的故障注入，不适用于 D1–D5 的主路径。
- **秘密的取用纪律**：`session_id` 秘密只存在两处——daemon 的 `runtime-state.json`（`jobs[].session_id`）与一次性 GIT_ASKPASS。D1 的 fencing 探针从前者取旧秘密属于演练特权；任何日志/事件/observe 面**不得**出现秘密，公开面只有 `session_fingerprint`（B3）。断言里若在 `events.log`/hub 响应中 grep 到秘密本身，即 B3 违规，直接判 FAIL。
- **节奏常数无可调旗**：M4 复验节奏 5 min、传输退避 30 s、调用上限 70 s 都是编译期常数（`observe/session.go`）；D5 的等待断言不要试图用环境变量缩短。
- **演练后清理**：每条演练收尾把票交给持有方正常收尾：`pfb wrap $WI`（或让 fakepi 计划自行 wrap）。wrap 成功的判据是 hub `session_fingerprint` 清空（`session.go` `End`：terminal 判定整行清 session）——`wi_session_fp $WI` 应返回空串。
